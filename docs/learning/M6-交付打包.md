## 核心知识点

### 1. asarUnpack：原生模块打包第一大坑

asar 是把源码打成一个归档文件，Electron 做了虚拟文件系统让 `require` 能读里面的 JS。但 `.node` 文件是**动态链接库**，要按真实文件路径 `dlopen` 加载——虚拟路径无法被动态链接器识别，留在 asar 里必崩。

```yaml
asarUnpack:
  - "**/node_modules/better-sqlite3/**"
  - "**/node_modules/hnswlib-node/**"
```

builder 会把它们原样放到 `app.asar.unpacked/` 并在 asar 内留解包标记，`require` 自动重定向。M6 的验证不是"打包成功"就算完——用包内 Node 直接 `require('app.asar/node_modules/better-sqlite3')` 跑了内存库读写、hnswlib 建索引检索 5 项断言，确认真能加载。

### 2. ABI 重编译为什么是必须的

Electron 内置的 Node 与系统 Node 的 `NODE_MODULE_VERSION`（ABI）可能不同。原生 C++ 插件按某个 ABI 编译，运行时 ABI 不匹配直接拒绝加载。`postinstall: electron-builder install-app-deps` 与打包时的 `@electron/rebuild` 都在干同一件事：针对 Electron 的头文件重编译原生模块。

### 3. 生产环境安全收敛（与开发态的区别对待）

在 [src/main/index.ts](../../src/main/index.ts)：

- **单实例锁** `requestSingleInstanceLock()`：第二次启动直接退出；`second-instance` 时唤起/聚焦已有窗口——否则两个实例抢同一个 SQLite、重复跑后台任务
- **导航拦截** `will-navigate`：单页壳应用拒绝任何整页导航，http(s) 外链转 `shell.openExternal`，`file:`/`javascript:` 等静默拦截
- **打包态收敛**：`app.isPackaged` 时移除默认菜单（含重新加载/DevTools 项）、`webPreferences.devTools=false`。开发态全部保留，调试不受影响
- 新窗口 `setWindowOpenHandler` 也有协议白名单（M5 Agent 的 open_url 白名单之外的第二道闸）

原则：**用 `app.isPackaged` 区分行为，而不是维护两套代码。**

### 4. 未签名应用的分发现实

没有 Apple Developer 账号时 `mac.identity: null` 显式跳过签名，产出 ad-hoc 包，可本机/内网分发。用户首次打开需右键 → 打开（或系统设置里允许），dmg 里放 Applications 软链做拖拽安装。将来要正式分发，再补 Developer ID 签名 + 公证（notarization），配置增量即可。

### 5. 设置备份：密钥为什么不导出

备份文件是 `{kind, appVersion, exportedAt, settings, hasApiKey}` 的 JSON。API Key 由 safeStorage 绑**机器级密钥**加密（Keychain/DPAPI），换机器根本无法解密——导出既无用又是泄露面，只记录"原机器上是否配过 Key"，导入后提示重新填写。

导入链路对外部文件零信任：先验 `kind` 防误选其他 JSON，再经 `sanitizeSettings` 逐字段按类型/枚举校验、只挑已知键、缺字段回退默认值。

### 6. 首次引导的状态设计

不新建表：在 `app_setting` key-value 表加一个 `ui_meta` 行存 `onboardingDismissedAt`。启动时为 null 就弹三步卡（配模型 → 导入资料 → 三种对话模式）。任何退出路径（开始使用/快捷跳转）都先持久化 dismiss 再跳转；查询失败则降级为不弹，引导永远不能挡住主界面。

### 7. 应用图标怎么做才不"AI 模板感"

最终方案（用户审美主导两轮筛选）：[resources/icon.svg](../../resources/icon.svg) 暖墨黑 squircle + 米白圆头粗笔字母 L（竖笔即灯柱）+ 顶端琥珀灯点。刻意不用渐变/光晕/星光。

工程要点：

- **小尺寸优先**：Dock 16px 下只有强对比几何笔画还可辨，复杂场景（书+灯+光）缩到 32px 必糊
- macOS 零三方工具链：SVG 用系统 Swift `NSImage`（11+ 原生支持 SVG）→ `NSBitmapImageRep` 出各尺寸 PNG → `iconutil -c icns` 组 iconset（16~512@2x）
- builder 按 `buildResources: resources` 约定自动拾取 `icon.icns`/`icon.png`，改完图标重跑 `npm run dist`

## 持续交付：GitHub Actions 自动打包分发

本地能打包只是起点，`.github/workflows/` 把发布变成"推一个标签"的事：

### 两条流水线的分工

| 文件 | 触发 | 干什么 |
|---|---|---|
| [ci.yml](../../.github/workflows/ci.yml) | push main / PR | ubuntu 上 `npm ci → typecheck → build`，分钟级红绿信号，保证主干随时可发版 |
| [release.yml](../../.github/workflows/release.yml) | 推送 `v*` 标签 | 三平台矩阵并行打包，产物自动挂到 GitHub Release |

矩阵三行（用**原生架构 runner** 而不是交叉编译，避开原生模块重编译的坑）：

```
macos-14 (Apple 芯片) → electron-builder --mac --arm64 → dmg + zip
macos-13 (Intel)      → electron-builder --mac --x64   → dmg + zip
windows-latest        → electron-builder --win --x64   → NSIS .exe
```

发布流程（版本号在 [package.json](../../package.json)）：

```bash
# 1. 改版本号
npm version 0.2.0 --no-git-version-tag   # 或手改 package.json
git commit -am "chore: release v0.2.0"
# 2. 打标签并推送——workflow 里的防呆步骤会校验 tag 与版本号一致
git tag v0.2.0
git push origin main --tags
# 3. Actions 页面等三个绿灯，Release 页面自动出现带产物的 v0.2.0
```

设计要点（都值得在自己的项目里复用）：

1. **`--publish never` + 统一上传**：builder 只管出包，上传 Release 统一用 `softprops/action-gh-release`，三个并行任务向同一个 Release 追加文件，避免 builder 各自的发布探测
2. **`fail-fast: false`**：一个平台挂了，另外两个照样出包
3. **标签/版本防呆**：`v0.2.0` 标签必须等于 `package.json` 的 `0.2.0`，否则任务失败——防止安装包版本号和 Release 标题对不上
4. **`permissions: contents: write`**：只给上传 Release 所需的最小权限；预发布标签（`v0.2.0-rc1`）自动标 prerelease
5. **缓存分层**：setup-node 缓存 npm 依赖，actions/cache 按平台缓存 Electron 二进制与 builder 依赖（`~/Library/Caches/electron` 等）
6. CI 刻意只跑 typecheck/build **不打包**：把"快速反馈"和"正式产物"两条流水线分开，日常推送不等几分钟的打包

### 未签名分发的边界（当前状态）

- macOS：`identity: null` 出 ad-hoc 包，用户首次右键 → 打开；将来要消除这一步，需 Apple Developer 账号 + Developer ID 签名 + 公证（notarization）
- Windows：NSIS 包无签名，首次运行有 SmartScreen 提示（更多信息 → 仍要运行）；消除需 EV/OV 代码签名证书

### 自动更新（electron-updater，已接入）

从"能分发"到"能自动更新"的完整链路：

- **更新源**：electron-builder.yml 的 `publish: { provider: github, owner, repo }` 有两个消费者——打包时生成 `app-update.yml` 装进应用（electron-updater 运行时读它知道去哪查更新）；builder 自己的发布动作仍由所有脚本/CI 显式 `--publish never` 关掉，产物统一走 softprops 上传
- **更新协议**：electron-updater 不查 GitHub API，而是拉 Release 附件里的元数据文件（Win `latest.yml`；mac `latest-mac.yml`），里面有版本号/文件名/sha512；下载对应安装包（Win 是 NSIS exe，mac 是 **zip** 不是 dmg——Squirrel.Mac 解压 zip 替换 .app），`.blockmap` 支持差量下载
- **产品策略**（src/main/services/update.ts）：启动 10s 后静默**检查**一次（避开启动抢资源），发现版本只通知不下载；设置页手动「下载更新」（进度/速率经 download-progress 事件推送）→「重启并安装」；`autoInstallOnAppQuit=true` 兜底，用户自然退出时也会装上
- **状态机可观测**：checking/available/not-available/downloading/downloaded/error 全部经 `update:event` 广播给渲染端，error 不弹框只落状态（后台断网检查不应打扰），设置页 error 时给 Releases 手动下载链接。经验：**autoUpdater 的 error 必须事件监听，只靠 checkForUpdates() 的 Promise reject 接不住下载阶段的失败**
- **mac 双架构分通道**（关键坑）：两个 mac runner 向同一 Release 目录传文件，默认元数据都叫 `latest-mac.yml` 会互相覆盖。解法是 CI 里把它分别改名成 `latest-arm64-mac.yml` / `latest-x64-mac.yml`，应用内按 `process.arch` 设 `autoUpdater.channel`（electron-updater 对 darwin 会给 channel 自动拼 `-mac` 后缀，`getChannelFilename` 再拼 `.yml`）。yml 内部引用的 zip 名本身带 -arm64/-x64，改名元数据不影响其内容
- **开发态**：`app.isPackaged` 为 false 时直接 unsupported（没有 app-update.yml、版本恒为 0.0.0，发请求毫无意义），IPC 仍注册，UI 显示"仅安装包可用"
- **未签名的现实**：Squirrel.Mac 安装未签名 zip 很可能被系统拒绝，所以 UI 保留手动下载入口；v0.1.0 安装包不含更新模块，必须手动跨一次版本
- electron-updater 是普通运行时依赖，externalizeDepsPlugin 自动外置；类型定义自带，主进程直接 `import { autoUpdater } from 'electron-updater'`

## 自测题参考答案

**1. 不配置 asarUnpack 直接打包，应用会在什么时刻、以什么方式失败？为什么 JS 文件没这个问题？**

失败时刻不是"打包时"，而是**用户启动应用、主进程第一次 require 原生模块时**：`better-sqlite3`/`hnswlib-node` 的 `.node` 本质是动态链接库（dylib/dll），Node 要用 `dlopen` 按一个真实存在的文件路径加载它。asar 只是 Electron 在 JS 层模拟出来的归档虚拟文件系统，动态链接器不认识 asar 内的虚拟路径，于是报"cannot find module / 动态库加载失败"，主进程崩溃，窗口起不来。

配了 `asarUnpack` 后，builder 把这两个包原样解到 `app.asar.unpacked/` 真实目录，asar 内的 require 路径被自动重定向过去，`dlopen` 拿到真实路径，正常。

JS 文件没这个问题，是因为它们由 Node/V8 自己读取并编译执行，Electron 对 asar 内的 JS 读写做了完整的虚拟文件系统桥接（读文件、seek 都能拦截）；而 `.node` 的消费者是操作系统的动态加载器，绕过了 Electron 的文件抽象，这层虚拟路径骗不过它。

**2. 系统 Node 里能 `require('better-sqlite3')`，为什么打进 Electron 后可能反而不行？**

因为原生 C++ 插件是按某个 **NODE_MODULE_VERSION（ABI 版本号）** 编译的，加载时运行时会严格比对。系统 Node 的 ABI 和 Electron 内置 Node 的 ABI 通常不同（Electron 还会带自己的 Chromium/V8 改动）。`npm install` 默认按系统 Node 头文件编译，所以系统 Node 能 require；Electron 加载这个 `.node` 时 ABI 校验不过，直接拒绝加载。

解决就是把插件针对 Electron 的头文件重编译：`electron-builder install-app-deps`（已挂在 postinstall，开发态 `ELECTRON_RUN_AS_NODE=1 electron` 跑测试也依赖它）和打包时 builder 自动执行的 `@electron/rebuild` 干的是同一件事。反过来同理：重编后系统 Node 又加载不了——所以冒烟测试必须用 `ELECTRON_RUN_AS_NODE=1 electron --test` 跑，不能用系统 node。

**3. 单实例锁解决了哪三个具体问题？**

`requestSingleInstanceLock()` 让第二个实例启动时直接退出，并由 `second-instance` 事件唤起已有窗口：

1. **数据库安全**：两个进程同时打开同一个 SQLite（即使有 WAL，也只有多读单写级别的并发保证），同一进程内的单例 better-sqlite3 连接 + 事务假设全部失效，可能出现锁竞争（SQLITE_BUSY）甚至写坏逻辑状态（两个进程跑各自的导入/迁移）。
2. **后台任务重复**：导入流水线、自动更新检查/下载、SSE 请求等后台任务会在两个实例里各跑一遍——同一文件重复 embed、同一更新包重复下载、通知与事件重复。
3. **用户体验**：用户从 Dock/开始菜单多点了一次图标，看不到新窗口（或一闪而过）却以为应用没反应，实际上旧窗口被挡在后面。单实例锁把第二个实例的启动参数/焦点转给已有窗口并置顶，符合"应用只有一个入口"的桌面直觉。

**4. 用户把备份 JSON 里的 provider 改成了非法值，导入后会发生什么？**

什么坏事都不会发生。导入链路对外部文件零信任：先校验 `kind === 'lumen-desk-settings'` 防误选其他 JSON，再经 `sanitizeSettings` 逐字段清洗。`provider` 的处理是白名单判断——只有严格等于 `'cloud'` 或 `'local'` 才采用，否则回落 `DEFAULT_SETTINGS.provider`。其余字段同理：字符串字段类型不对回默认值、数字字段要求有限数、未知键直接忽略。

所以非法 provider 不会进入数据库、不会让 resolver 崩溃、也不会卡住聊天；代价仅仅是该用户的这个偏好被默认值覆盖。全量数据备份（t6）的 `restoreDataBackup` 采用同一套 sanitize 思路，脏枚举（mode/status/stepType）都回落安全默认值，整条/整块缺 id 才丢弃。

**5. 为什么图标要先画 32px 而不是先画 1024px？**

因为图标的主要使用尺寸是极小的：Dock 常见 16–48px、任务栏/关于面板也就几十像素。先在 1024px 画布上画细节（渐变、光晕、书本+灯的场景），缩小后笔画糊成一团、对比消失、认不出是什么——大图好看不代表小图可用。

先画 32px 强迫设计在"最差可见条件"下成立：只能靠强对比的几何形状和粗笔画（墨黑 squircle + 米白粗体 L + 一颗琥珀灯点），32px 下可辨，放大到 1024 自然也成立。这与 UI 设计的通用原则一致：先约束最难的场景。技术上 mac 图标链路是 SVG → NSImage/NSBitmapImageRep 出 16~512@2x 各尺寸 PNG → `iconutil` 组 icns，每个尺寸都来自同一矢量稿，但设计验收以小尺寸为准。

**6. 未签名的 dmg 发给另一位 Mac 用户，他第一次打开需要做什么？要消除这一步需要什么资质和配置？**

首次打开 Gatekeeper 会拦截（"无法验证开发者，无法打开"或"已损坏，应该移到废纸篓"——后者其实也是隔离标志）。放行方式二选一：

- Finder 里**右键（或 control+点击）应用 → 打开**，弹窗里会多出"打开"按钮，点一次后以后不再拦；
- 命令行 `xattr -dr com.apple.quarantine "/Applications/Lumen Desk.app"` 去掉隔离属性。

另外 dmg 安装流程是拖到 Applications；从外置磁盘直接跑未签名应用还可能有 sandbox 提示。

要彻底消除：加入 Apple Developer Program（年费 99 美元），用 **Developer ID Application 证书签名**（`electron-builder.yml` 的 mac.identity 指定，不再是 null），再走 **notarization（公证）**——把包提交给 Apple 自动安全检查，票据 stapled 到应用上，Gatekeeper 才会直接放行。Windows 侧对应的是代码签名证书（OV/EV）消 SmartScreen。这也是自动更新在 mac 上的前提之一：Squirrel.Mac 安装未签名 zip 很可能失败，只能引导手动下载 dmg。

**7. 为什么 release 矩阵里 mac 两个架构分别用 macos-14 / macos-13 原生 runner，而不是在一台机器上交叉编译？**

因为项目有两个原生 C++ 模块（better-sqlite3、hnswlib-node），打包前要按**目标架构 + Electron ABI** 重编译。交叉编译（在 arm64 机器上编 x64 或反过来）需要完整的跨工具链、正确的 `--target_arch`、arm64 机器上还要 Xcode 命令行工具同时具备两套 slice，任何一处不对就产出"架构错误的 .node"，且往往要到用户机器上才 dlopen 失败。

用原生 runner：macos-14 是 Apple Silicon 直接出 arm64、macos-13 是 Intel 直接出 x64，`@electron/rebuild` 编本机架构最稳；Windows 用 windows-latest 出 exe 同理。三行矩阵并行还更快。代价只是多耗 CI 分钟数，换来零交叉编译排坑。

**8. 打完标签发现 package.json 版本号忘改了，workflow 会在哪一步、以什么方式阻止你？**

在矩阵每个任务的"校验标签与 package.json 版本一致"步骤（build 之前）失败：脚本取 `GITHUB_REF_NAME`（如 `v0.3.0`）和 `node -p "require('./package.json').version"` 前加 v 后做字符串比较，不一致就 `echo "::error::…"` 并 `exit 1`。CI 任务红掉，后面的 `npm run build`、electron-builder 打包、Release 上传都不执行，也就不会产生"Release 标题写 v0.3.0、安装包关于窗口显示 0.2.0、electron-updater 元数据也是 0.2.0"的灾难。修复方式：改 package.json 版本、提交、**删掉错误标签重打**（`git tag -d v0.3.0 && git push origin :refs/tags/v0.3.0` 后重新 tag）。

**9. 日常 push main 时会触发完整打包吗？为什么要把质量门和发布流水线分开？**

不会。两条流水线触发条件不同：ci.yml 在 push main / PR 时只跑 `npm ci → typecheck → 冒烟测试 → 三端 build`，分钟级；release.yml 只在推送 `v*` 标签时才跑三平台 electron-builder 完整打包（单平台数分钟到十几分钟）。

分开的理由：① 反馈速度——每次提交都等 dmg/exe 打包，主干开发节奏被拖死；② 成本——GitHub Actions 分钟数有限，打包还涉及 Electron 二进制下载、三平台矩阵；③ 语义——main 的 HEAD 不保证是可发布状态，"能编译通过"和"可以发给用户"是两件事，打标签这个显式动作才是发布意图；④ 质量门必须在 PR 阶段就拦住问题，发布流水线只负责忠实产出。

**10. macOS 上 `setApplicationMenu(null)` 为什么会让打包后的 ⌘C/⌘V 失效，而开发态却没问题？为什么 Win/Linux 不受影响？**

因为 macOS 的编辑命令路由挂在应用菜单的标准 role 上：⌘X/⌘C/⌘V/⌘A、中文输入法候选词提交等快捷键，实际是由「编辑菜单」里 `role: 'cut'/'copy'/'paste'/'selectAll'` 的标准菜单项承载的，role 菜单还自带系统本地化和标准快捷键绑定。把应用菜单整个置空后，这些命令没有了路由目标，快捷键就失效了。

开发态没问题是因为 Electron 在开发模式会自动注入一套默认菜单（含 app/edit/view/window 完整 role），把这个问题掩盖了；打包后默认菜单不再自动出现，置空就是真空。这是"框架在开发态帮你补的东西，生产态都要假设没有"的典型案例。修复：darwin 下显式 `Menu.buildFromTemplate([{role:'appMenu'},{role:'editMenu'},{role:'windowMenu'}])`。

Win/Linux 不受影响：这两个平台上编辑快捷键在输入控件层直接处理（Chromium 的焦点/编辑命令路径），不依赖应用菜单栏，所以可以置空菜单换取更干净的桌面应用外观。

**11. electron-updater 在 macOS 上下载的是 dmg 还是 zip？为什么两个 mac 架构要把 latest-mac.yml 改名分通道，改名后为什么不影响下载？**

下载的是 **zip**，不是 dmg。mac 侧自动更新走 Squirrel.Mac：下载 zip → 校验 yml 里的 sha512 → 解压出新 `.app` 替换旧的。dmg 只是给人手动拖拽安装用的。所以 Release 必须同时上传 zip 和 yml（dmg 可有可无，本项目两个都传）。

分通道原因：electron-updater 默认在 Release 目录找固定文件名 `latest-mac.yml`。arm64、x64 两个 runner 并行往同一个 GitHub Release 传同名文件，后上传的覆盖先上传的，结果某一个架构的应用会拿到错误架构的元数据 → 下载的 zip 架构不匹配、更新失败。解法是 CI 把各自的 `latest-mac.yml` 复制改名成 `latest-arm64-mac.yml` / `latest-x64-mac.yml`，应用内按 `process.arch` 设 `autoUpdater.channel`——electron-updater 对 darwin 平台会把自定义 channel 拼成 `${channel}-mac` 再补 `.yml`（源码 Provider.getCustomChannelName 可验证），正好请求到改名后的文件。

改名不影响下载：yml 只是"更新清单"，文件**内部**用相对路径记录真正的安装包文件名（`Lumen Desk-0.2.0-arm64.zip` / `-x64.zip`）与各自 sha512，这些文件名由 builder 按 `--arm64`/`--x64` 参数生成，本来就带架构后缀，与元数据文件自身叫什么名字无关。

**12. 为什么本项目只在启动后静默"检查"而不自动下载？后台检查失败为什么不能靠 Promise catch 发现？**

策略选择（services/update.ts）：启动 10 秒后静默检查一次，但 `autoDownload=false`——

- 安装包 100MB+，启动时自动偷跑下载会抢用户正在用的网络、占磁盘、笔记本耗电，用户毫无预期；
- 桌面应用的更新应该"知情、可控"：发现新版本只在设置入口亮红点，用户主动点「下载更新」（有进度/速率），下载完再决定何时「重启并安装」；`autoInstallOnAppQuit=true` 做了折中——已下载的包在用户自然退出时静默装好，不强制中断工作；
- 延迟 10 秒也避开了应用启动期的 CPU/IO 高峰。

失败为什么不能只靠 Promise catch：`checkForUpdates()` 的 Promise 只覆盖"这一次检查调用"的抛出；但更新是长生命周期的事件流——**下载阶段**的网络中断、校验失败等错误发生时，调用方代码根本不在 await（用户点完下载已经回去干别的了），没有任何 Promise 可以 catch。electron-updater 因此提供 `error` 事件，所有阶段的失败都经事件出来，必须订阅 `autoUpdater.on('error', ...)` 落到 UpdateState 并广播给渲染端。后台静默检查（断网、GitHub 限流）按"不打扰"原则只落状态不弹框，用户打开设置时能看到原因和手动下载链接。
