# M1 · 流式聊天

> 对应提交：`68ec9cd` → `f46570f`（共 16 个）
> 目标：像 ChatGPT 一样逐字输出、能随时停止、关掉窗口再打开历史还在。

## 解决什么问题

M0 只能 ping。M1 要补齐一个聊天产品的最小闭环，四个硬需求：

1. **流式渲染**（F-A1）：模型一个 token 一个 token 地吐字，界面逐字显示
2. **随时停止**：生成中点"停止"立即中断网络请求
3. **历史持久化**（F-A3）：会话/消息落 SQLite，重启不丢
4. **上下文管理**（F-A2）：长对话超窗口时自动压缩早期历史

## 架构与数据流

```
渲染端 Composer
  │ invoke('chat:run', {conversationId?, mode:'chat', message})
  ▼
ipc/chat.ts executeRun
  1. 用户消息 + assistant 占位(status=streaming) 先落库
  2. 组装历史 → compactIfNeeded（超 80% 阈值先摘要压缩）
  3. resolveModelConfig 拿到 {baseUrl, apiKey, model}
  4. streamChatCompletion(...)  ◄── async generator
  5. 每个 delta：webContents.send('chat:event', {type:'token'})
                  同时累积 answer
  6. 结束：一次 UPDATE 占位消息为完整文本 + usage（status=done）
  7. 任何异常：{type:'error'}，占位消息 status=error
  │
  ▼ （推送方向，全部走同一个频道 chat:event）
preload onEvent 回调 → useChat.handleEvent（唯一 reducer）→ Zustand → React
```

停止链路：

```
渲染点停止 → invoke('chat:stop', streamId)
           → 找到该次运行的 AbortController.abort()
           → fetch 中断，generator 抛 AbortError
           → 上层识别为"主动停止"：已生成的部分照常落库，不报错
```

关键时序约定：**用户消息和 assistant 占位先落库，流结束只做一次 UPDATE**。这样无论崩溃/强退发生在哪一步，数据库里都有完整的消息骨架，不会出现"界面聊过、库里没有"。

## 核心知识点

### 1. SSE 在传输层到底是什么

就是一个普通 HTTP POST，响应头 `Content-Type: text/event-stream`，响应体是源源不断的文本帧：

```
data: {"choices":[{"delta":{"content":"你好"}}]}

data: {"choices":[{"delta":{"content":"，"}}]}

data: [DONE]
```

Node 里 `res.body.getReader()` + `TextDecoder` 按块读。**注意一个 chunk 不一定恰好是一行**：可能半行、也可能多行粘在一起，必须维护 `buffer`，按 `\n` 切、留残尾。最后一帧 `choices` 可能是空数组、usage 单独出现（OpenAI 加 `stream_options.include_usage:true` 的约定）。

手写一遍能理解：流式不是什么特殊协议，就是"不结束的 HTTP 响应 + 约定的行格式"。

### 2. AbortController 是停止功能的全部秘密

`fetch(url, { signal })` 把中断权交出来。UI 层只管维护 `streamId → controller` 的 Map，停止时调一下 `abort()`，网络读取处自然抛 `AbortError`。**主动停止和真实错误必须区分对待**：停止时已收到的文本要正常落库，界面也不显示红色错误条。

### 3. SQLite 在桌面应用的正确打开方式

- **单例连接**：整个应用复用一个 `Database` 实例（better-sqlite3 是同步 API，没有连接池概念）
- **WAL 模式**：`PRAGMA journal_mode=WAL`，读写不互锁，崩溃也不易损库
- **外键默认是关的**：必须显式 `PRAGMA foreign_keys=ON`，`ON DELETE CASCADE` 才生效
- **主键用应用层 uuid（TEXT）** 而不是自增整数：数据迁移、同步、客户端生成都不被序号绑架

### 4. 幂等迁移：老用户的库怎么加列

`schema.sql` 用 `CREATE TABLE IF NOT EXISTS` 只能建新表，**不能给已存在的表加列**。迁移框架 `runMigrations()` 的套路：

```ts
const cols = conn.prepare('PRAGMA table_info(message)').all()
if (!cols.some(c => c.name === 'meta')) conn.exec('ALTER TABLE message ADD COLUMN meta TEXT')
```

检查存在性再 ALTER，启动时跑一遍天然幂等。M3/M5 的所有表结构演进都走这同一条路。

### 5. 上下文压缩：零 tokenizer 依赖的估算

不需要精确 token 数，只需要一个**单调、便宜**的近似来决定何时压缩：CJK 字符约 1 字 1 token，其他约 4 字符 1 token。超过窗口的 80% 时，用一次 LLM 调用把除最近 8 条之外的历史压成摘要，以一条 system 消息替换。这是"用一次小成本避免一次硬失败（400 context length）"。

### 6. 密钥绝不进数据库

API Key 用 Electron `safeStorage` 加密后写 `secrets.enc`（macOS 底层是 Keychain）。渲染端永远只能看到 `hasApiKey: true/false`，设置弹窗里密钥框留空 = 不修改，从机制上杜绝"把一串星号误存成新 Key"。

## 踩坑记录

- **SSE 残包**：忘记 buffer 残行会偶发 JSON.parse 失败，且在长回答时必现——这类问题只在"chunk 边界不巧"时出现，本地 mock 很难复现。
- **Electron 44 + better-sqlite3 ABI**：原生模块要按 Electron 内置的 Node ABI 重编译，`postinstall: electron-builder install-app-deps` 就是干这个的；直接用系统 Node 的 ABI 装，运行时报 `NODE_MODULE_VERSION mismatch`。
- 相对路径层级三处写错（`176bd0f`）：深一层目录的 service 引 db 是 `../../db`，services 根下直接引是 `../db`——靠严格 typecheck 兜底。
