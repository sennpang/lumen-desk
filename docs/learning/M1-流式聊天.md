# M1 · 流式聊天

> 对应提交：`68ec9cd` → `f46570f`（共 16 个）
> 目标：像 ChatGPT 一样逐字输出、能随时停止、关掉窗口再打开历史还在。

## 解决什么问题

M0 只能 ping。M1 要补齐一个聊天产品的最小闭环，四个硬需求：

1. **流式渲染**（F-A1）：模型一个 token 一个 token 地吐字，界面逐字显示
2. **随时停止**：生成中点"停止"立即中断网络请求
3. **历史持久化**（F-A3）：会话/消息落 SQLite，重启不丢
4. **上下文管理**（F-A2）：长对话超窗口时自动压缩早期历史

## 架构与数据流

```
渲染端 Composer
  │ invoke('chat:run', {conversationId?, mode:'chat', message})
  ▼
ipc/chat.ts executeRun
  1. 用户消息 + assistant 占位(status=streaming) 先落库
  2. 组装历史 → compactIfNeeded（超 80% 阈值先摘要压缩）
  3. resolveModelConfig 拿到 {baseUrl, apiKey, model}
  4. streamChatCompletion(...)  ◄── async generator
  5. 每个 delta：webContents.send('chat:event', {type:'token'})
                  同时累积 answer
  6. 结束：一次 UPDATE 占位消息为完整文本 + usage（status=done）
  7. 任何异常：{type:'error'}，占位消息 status=error
  │
  ▼ （推送方向，全部走同一个频道 chat:event）
preload onEvent 回调 → useChat.handleEvent（唯一 reducer）→ Zustand → React
```

停止链路：

```
渲染点停止 → invoke('chat:stop', streamId)
           → 找到该次运行的 AbortController.abort()
           → fetch 中断，generator 抛 AbortError
           → 上层识别为"主动停止"：已生成的部分照常落库，不报错
```

关键时序约定：**用户消息和 assistant 占位先落库，流结束只做一次 UPDATE**。这样无论崩溃/强退发生在哪一步，数据库里都有完整的消息骨架，不会出现"界面聊过、库里没有"。

> streamId 是怎么把"下单"和"几百次推送"关联起来的——这些 IPC 内部机制在
> [M0「IPC 深入：两种通信方向的内部原理」](M0-electron-骨架.md#ipc-深入两种通信方向的内部原理)

## 核心知识点

### 1. SSE 在传输层到底是什么

就是一个普通 HTTP POST，响应头 `Content-Type: text/event-stream`，响应体是源源不断的文本帧：

```
data: {"choices":[{"delta":{"content":"你好"}}]}

data: {"choices":[{"delta":{"content":"，"}}]}

data: [DONE]
```

Node 里 `res.body.getReader()` + `TextDecoder` 按块读。**注意一个 chunk 不一定恰好是一行**：可能半行、也可能多行粘在一起，必须维护 `buffer`，按 `\n` 切、留残尾。最后一帧 `choices` 可能是空数组、usage 单独出现（OpenAI 加 `stream_options.include_usage:true` 的约定）。

手写一遍能理解：流式不是什么特殊协议，就是"不结束的 HTTP 响应 + 约定的行格式"。

### 2. AbortController 是停止功能的全部秘密

`fetch(url, { signal })` 把中断权交出来。UI 层只管维护 `streamId → controller` 的 Map，停止时调一下 `abort()`，网络读取处自然抛 `AbortError`。**主动停止和真实错误必须区分对待**：停止时已收到的文本要正常落库，界面也不显示红色错误条。

### 3. SQLite 在桌面应用的正确打开方式

- **单例连接**：整个应用复用一个 `Database` 实例（better-sqlite3 是同步 API，没有连接池概念）
- **WAL 模式**：`PRAGMA journal_mode=WAL`，读写不互锁，崩溃也不易损库
- **外键默认是关的**：必须显式 `PRAGMA foreign_keys=ON`，`ON DELETE CASCADE` 才生效
- **主键用应用层 uuid（TEXT）** 而不是自增整数：数据迁移、同步、客户端生成都不被序号绑架

### 4. 幂等迁移：老用户的库怎么加列

`schema.sql` 用 `CREATE TABLE IF NOT EXISTS` 只能建新表，**不能给已存在的表加列**。迁移框架 `runMigrations()` 的套路：

```ts
const cols = conn.prepare('PRAGMA table_info(message)').all()
if (!cols.some(c => c.name === 'meta')) conn.exec('ALTER TABLE message ADD COLUMN meta TEXT')
```

检查存在性再 ALTER，启动时跑一遍天然幂等。M3/M5 的所有表结构演进都走这同一条路。

### 5. 上下文压缩：零 tokenizer 依赖的估算

不需要精确 token 数，只需要一个**单调、便宜**的近似来决定何时压缩：CJK 字符约 1 字 1 token，其他约 4 字符 1 token。超过窗口的 80% 时，用一次 LLM 调用把除最近 8 条之外的历史压成摘要，以一条 system 消息替换。这是"用一次小成本避免一次硬失败（400 context length）"。

### 6. 密钥绝不进数据库

API Key 用 Electron `safeStorage` 加密后写 `secrets.enc`（macOS 底层是 Keychain）。渲染端永远只能看到 `hasApiKey: true/false`，设置弹窗里密钥框留空 = 不修改，从机制上杜绝"把一串星号误存成新 Key"。

## 深入：逐行走读流式客户端的四个关键机制

上面的知识点给的是结论，这一节对照 [client.ts](../../src/main/services/llm/client.ts) 真实代码把四个"为什么"拆到底。

### A. 一次完整的读取循环：buffer 里到底发生了什么

核心循环只有两层 while，但它同时处理了"半帧、粘帧、多字节字符切割"三件事：

```ts
const reader = res.body!.getReader()      // 拿到 HTTP 响应体的字节流读取器
const decoder = new TextDecoder()         // 字节 → 字符串；UTF-8
let buffer = ''                           // 跨 chunk 残留的"半行"

while (true) {
  const { done, value } = await reader.read()   // value 是 Uint8Array，不是字符串
  if (done) break
  buffer += decoder.decode(value, { stream: true })  // ① 字节解码后追加

  let nlIndex: number
  while ((nlIndex = buffer.indexOf('\n')) >= 0) {    // ② 能切出几行就处理几行
    const line = buffer.slice(0, nlIndex).trim()
    buffer = buffer.slice(nlIndex + 1)               // ③ 切走的行离开 buffer
    if (!line.startsWith('data:')) continue          // 空行/注释行/事件行：忽略
    const data = line.slice(5).trim()
    if (data === '[DONE]') return /* 收尾 */
    const json = JSON.parse(data)                    // ④ 到这一步，data 必是完整 JSON
    const delta = json.choices?.[0]?.delta
    if (delta?.content) { content += delta.content; yield delta.content }
  }
  // 内层 while 退出时，buffer 里要么是空，要么是一段不含 \n 的残尾——
  // 它就是"半帧"，不 parse、不丢弃，等下一次外层 read 拼上新字节
}
```

用一个具体例子走一遍。假设网络把模型响应切成三个 TCP 包到达：

```
第 1 包字节：data: {"choices":[{"delta":{"content":"你"}}]}\n\nda
第 2 包字节：ta: {"choices":[{"delta":{"content":"好"}}]}\n\n
第 3 包字节：data: [DONE]\n\n
```

- 处理第 1 包：内层 while 切出完整的第一帧（yield "你"），buffer 里**剩下 `da`**——这是下一帧 `data:` 的前两个字节。它不含换行，内层循环退出，残尾静静躺着。
- 第 2 包到达：`buffer = 'da' + 'ta: {...好...}\n\n'`，残尾和新字节拼成完整的第二帧，正常 parse 出"好"。
- 第 3 包：切出 `data: [DONE]`，return 收尾。

如果没有 buffer，第 1 包结束时你要么 parse `da` 直接炸、要么丢掉残尾导致下一帧变成 `ta: ...` 无法识别。**"读到字节先追加、只消费完整行、残尾留下"这三个动作的顺序不能换**——这是所有行协议（SSE、NDJSON、Redis RESP）解析器的共同骨架。

### B. `decoder.decode(value, { stream: true })` 的 stream:true 为什么不能省

这是比半帧更隐蔽的一层：TCP 切的是**字节**，而一个中文字在 UTF-8 里占 3 个字节（"你" = `E4 BD A0`）。完全可能前一个包的结尾只来了 `E4 BD`，第三个字节 `A0` 在下一个包里。

- 不传 `{stream:true}`：TextDecoder 每片都当作"完整文本"解码，结尾不完整的字节序列会被替换成 �（replacement character），"你好"变成"�好"，且无法挽回。
- 传 `{stream:true}`：解码器内部**缓存不完整的尾部字节**，等下一片来了拼上再解码，多字节字符永远不会被腰斩。

注意这层"字节残尾缓存"和 A 节的"行残尾缓存 buffer"是**两层不同的东西**：decoder 管跨 chunk 的半个字符，字符串 buffer 管跨 chunk 的半行数据。一层都不能少。

### C. async generator：yield 出去的字是怎么到 UI 的

`streamChatCompletion` 声明成 `async function*`，调用它不会立刻发请求，而是返回一个**异步生成器对象**；第一次 `for await` 才开始执行函数体，执行到 `yield delta.content` 就**暂停整个函数**（局部变量 content、buffer、reader 全部冻结在现场），把 delta 交给消费方，消费方拿下一个值时函数从暂停处原样恢复。

调用链是一条三段的"逐字管道"，没有任何一步在攒完整答案：

```
client.ts  yield delta（解析出一帧就暂停）
   ▲ for await
chat.ts executeRun：每片 emit(target, {type:'token', streamId, delta})
   ▼ webContents.send（M0 深入节讲过的推送方向）
useChat handleEvent：delta 追加到当前 assistant 消息文本（Zustand state）
   ▼ React 重渲染
MessageBubble 重新渲染，多了一个字 + 流式光标
```

生成器的"返回值"（`return { content, promptTokens, toolCalls }`）和 yield 的东西不一样：yield 是**过程中**吐出的增量，return 是**结束时**的总结算。消费方写法是 `const result = await stream.next()` 循环或本项目压缩里那种 `for await ... 完后用生成器返回值`——chat.ts 通过 try/finally 后的返回拿到全文与 usage 做那一次 UPDATE。理解这个区别就明白为什么"流到 UI 的字"和"最后落库的完整文本"不需要两套来源：增量给人看，同一个函数的累积 content（`content += delta.content`）给库存。

### D. abort() 之后，错误是怎么一路传播的

停止按钮的调用链：

```
UI invoke('chat:stop', streamId)
  → chat.ts 从 activeRuns 取 ActiveRun.controller.abort()
```

AbortController 本身不"杀线程"，它只是把关联的 signal 置为 aborted 状态并派发 abort 事件。真正响应它的是 fetch 基础设施：**正在进行的 HTTP 请求被中止，`reader.read()` 的 await 立刻以 AbortError reject**（已经到了操作系统缓冲区的字节不管了，底层 socket 由 finally 里的 `reader.releaseLock()` 配合 fetch 清理关闭）。

传播路径：

```
reader.read() reject AbortError
  → 从 for-await 抛出，跳出 generator（finally 执行 releaseLock，连接必释放）
  → chat.ts executeRun 的 for await 捕获到
  → 判断 e.name === 'AbortError' → 识别为"用户停止"而非 error：
      · content 里已累积的文本照常 UPDATE 落库（status='done'）
      · emit done（不是 error），UI 不弹红条
      · activeRuns.delete(streamId)
```

关键设计：**错误类型分流**。AbortError 和网络错误（ECONNRESET）、401 在同一条 await 上抛出，代码必须在 catch 点用 `e.name === 'AbortError'`（或 signal.aborted）把"用户主动"和"真故障"分开——前者按正常结束收尾，后者才 emit error。M5 在 abort 之前还要先 resolve 挂起的审批 Promise（见 M5 深入节），因为 abort 只能影响 fetch，碰不到用户自己 await 的 Promise。

### E. 上下文压缩：阈值、估算与 messages 数组变形

窗口管理的决策只依赖一个便宜的单调函数（[context.ts](../../src/main/services/llm/context.ts)）：

```ts
export function estimateTokens(text: string): number {
  let cjk = 0, other = 0
  for (const ch of text) {
    const code = ch.codePointAt(0) ?? 0
    const isCjk = (0x4e00<=code&&code<=0x9fff) || (0x3040<=code&&code<=0x30ff) || (0xac00<=code&&code<=0xd7af)
    isCjk ? cjk++ : other++
  }
  return cjk + Math.ceil(other / 4)   // CJK 约 1 字 1 token，英文约 4 字符 1 token
}
```

为什么敢用这么糙的估算？因为它的用途不是计费，而是**和阈值比大小**——阈值取窗口的 80%，留了 20% 安全边际，估算偏差 20% 也不会导致误判；而精确 tokenizer（tiktoken/gpt-tokenizer）要么体积大要么模型间不通用，为一个"何时触发"的判断不值得。每条消息额外 +4 是角色/结构包装的经验开销。

超限时数组发生一次"头部塌缩"（KEEP_RECENT=8）：

```
压缩前：[system, u1, a1, u2, a2, ..., u20, a20]   （tokens > 窗口 80%）
                 └────────── head（送去摘要）─────────┘  └ tail 原文保留 ┘
压缩后：[system, {role:'system', content:'【早期对话摘要】…'}, u17, a17, ..., u20, a20]
```

摘要是**另一次普通的流式 LLM 调用**（temperature 0.2 求稳定），复用同一个 streamChatCompletion——这里用 `for await` 把流消费成一个完整字符串，说明流式接口天然可以当非流式用，反过来则不行。transcript 截断 12000 字符是防止"为了省 token 的摘要请求自己先超长"。注意边界：如果全部消息都在最近 8 条里却仍超限（单条消息巨长），没有 head 可压，直接原样返回交给模型窗口硬扛——压缩不是万能的，别让它在这种情况下产生空摘要。

### F. 密钥链路：明文、密文各待在哪

safeStorage 不是加密算法库，它是**操作系统密钥设施的代理**：`encryptString(明文)` 时，Electron 向 Keychain/DPAPI 索要（或创建）一个属于本应用的密钥，用它在本地加密，返回密文 Buffer；应用代码永远看不到也存不下那把密钥。所以整条链路是：

```
保存：渲染端输入明文 → IPC（只走 invoke，不落日志）→ saveCloudApiKey
      → safeStorage.encryptString：明文 Buffer → 密文 Buffer
      → base64 编码 → 写进 secrets.enc（JSON），文件权限 0o600
      → 明文只写入主进程内存变量 plaintextCache
读取：getCloudApiKey → 读密文 → Buffer.from(base64) → safeStorage.decryptString → 明文
      （解密动作由 OS 完成：Keychain 里取出应用密钥；换机器/换用户就取不到）
```

[secrets.ts](../../src/main/store/secrets.ts) 里有一条注释值得专门理解——**内存明文缓存与磁盘密文绝不能混进同一个变量**：保存后本会话还要继续用明文请求模型，如果缓存里放的是密文，下次"取密钥"时会把 base64 密文当明文送进 `Authorization: Bearer`（401）或误送去 `decryptString`（抛错）。所以代码维护两个形态：`onDisk`（只装密文）负责写文件，`plaintextCache`（只装明文）负责运行时，一次保存里两者各自赋值、互不覆盖。`isEncryptionAvailable()` 的检查则是给 Linux 无 keyring 守护进程的环境一个明确报错，而不是默默写明文。

## 踩坑记录

- **SSE 残包**：忘记 buffer 残行会偶发 JSON.parse 失败，且在长回答时必现——这类问题只在"chunk 边界不巧"时出现，本地 mock 很难复现。
- **Electron 44 + better-sqlite3 ABI**：原生模块要按 Electron 内置的 Node ABI 重编译，`postinstall: electron-builder install-app-deps` 就是干这个的；直接用系统 Node 的 ABI 装，运行时报 `NODE_MODULE_VERSION mismatch`。
- 相对路径层级三处写错（`176bd0f`）：深一层目录的 service 引 db 是 `../../db`，services 根下直接引是 `../db`——靠严格 typecheck 兜底。

## 自测题参考答案

**1. 为什么用户消息和 assistant 占位要在流式开始之前落库？**

核心是**崩溃一致性**：流式输出可能持续几十秒，期间随时可能发生用户强退、断电、进程崩溃。先把两条记录（user 完整文本 + assistant 的 `status='streaming'` 占位）写进 SQLite，之后无论死在哪一步，数据库里都有完整的对话骨架：

- 流式正常结束：只做一次 UPDATE，把占位消息更新为完整文本、usage、`status='done'`。写库次数最少（每个 token 都写库会把 WAL 打爆）。
- 中途崩溃：重启后历史里至少能看到"用户问了什么 + 有一条没答完的消息"，而不是"界面上明明聊过、库里查无此记录"。重新生成功能也依赖"最后一条 user 消息可查"。
- 主动 stop：部分文本照样 UPDATE 进同一条占位消息，不需要特殊的插入路径。
- 另外 `seq` 在同一个事务里按会话分配（`UNIQUE(conversation_id, seq)`），先落库也固定了两条消息的排序，UI 与历史重建永远按 seq 有序。

**2. SSE 的一个 TCP chunk 里可能出现哪些边界情况？代码里怎么处理？**

TCP 是字节流，不保证"一次 read = 一帧"。可能出现：

- 半帧：一次 chunk 只读到 `data: {"choices":[{"delta":{"content":"你`，JSON 还没闭合；
- 粘帧：一次 chunk 里读到多行，甚至完整的好几帧；
- 半帧 + 粘帧同时出现：开头是上一帧的残尾，结尾是下一帧的半截；
- 空行分隔（SSE 规范用空行分隔事件）、`\r\n` 与 `\n` 行尾差异；
- 终止标记 `data: [DONE]` 单独成行；最后一帧 `choices` 可能是空数组、usage 单独出现。

处理方式（见 client.ts 的 SSE 读取循环）：用 `ReadableStream` 的 reader + `TextDecoder` 持续读字节，维护一个 `buffer` 字符串——每读到新 chunk 就追加到 buffer，按 `\n` 切出所有完整行，最后一段不完整的残尾**留在 buffer 里等下一片**；每行去掉 `data:` 前缀，遇 `[DONE]` 结束循环，取数据时对 `choices?.[0]?.delta?.content` 做防御式访问（数组可能为空）。这类 bug 的特点是长回答必现、本地 mock 难复现，因为它完全取决于网络怎么分包。

**3. 用户点停止后，`AbortError` 走到收尾逻辑时应该做哪几件事？哪些事不该做？**

应该做：

1. 中断信号识别为"用户主动停止"而不是错误（AbortController 的 abort 导致 fetch 抛出的 AbortError）；
2. 把已累积的部分文本通过那一次 UPDATE 写进占位消息，`status='done'`（有多少存多少）；
3. 给渲染端发正常的结束事件（done），让流式光标消失、输入框恢复可用；
4. 从活动运行注册表（streamId → controller / ActiveRun）里摘掉本次运行，释放资源。

不该做：

- 不该把消息标成 `error`、不该在界面上弹红条——停止是用户的正常操作；
- 不该丢弃已经生成的文本（那是用户等着看的部分回答）；
- 不该回滚/删除用户消息；
- M5 还要注意：不能只 abort fetch——必须**先把挂起的审批 Promise 全部 `resolve(false)`**（否则审批 Map 泄漏、循环永挂），再 abort 模型请求。

**4. 给一张老用户的库（没有 message.meta 列），应用启动时会发生什么？为什么不会重复加列？**

启动走 `initDb()`：打开单例连接、设 PRAGMA、执行带 `IF NOT EXISTS` 的 `schema.sql`（只保证新表存在），然后跑 `runMigrations()`。迁移里对每列做存在性检查：

```ts
const cols = conn.prepare('PRAGMA table_info(message)').all()
if (!cols.some(c => c.name === 'meta')) {
  conn.exec('ALTER TABLE message ADD COLUMN meta TEXT')
}
```

老库没有 `meta` 列 → 检查不通过 → 执行一次 ALTER 加上，老行该列为 NULL（读的时候按"无 meta"处理，比如没有 citations）。下次启动再跑同样的代码，`table_info` 里已经能查到 `meta`，条件为 false，ALTER 不再执行——幂等的关键就是"**每步迁移都以'检查当前 schema 是否已经是目标状态'为前提**"，而不是记录"我跑过没有"（版本号/迁移表可能丢，列不会骗人）。

**5. safeStorage 加密的 Key 换一台电脑能解密吗？**

不能。Electron `safeStorage` 在 macOS 底层用 Keychain、Windows 用 DPAPI，加密密钥绑定**当前操作系统用户/机器级的密钥体系**：密文离开这台机器（甚至换另一个系统用户）就没有对应的解密密钥，`safeStorage.decryptString` 会失败。

这直接决定了备份的设计：设置备份和全量数据备份都**不导出 API Key 明文也不导出密文**（密文拿过去也是无法解密的垃圾，还白白增加泄露面），只导出 `hasApiKey` 这种事实位，导入后提示用户重新填写。同理 HNSW 向量文件虽然不涉及密钥，但绑定本机模型维度/路径，也同样被排除在备份外。
