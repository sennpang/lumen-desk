# M4 · 混合检索

> 对应提交：`92b697d` → `de81c53`（共 3 个）
> 目标：语义召回（"意思对"）与关键词召回（"字面准"）取长补短，用 RRF 融合成一路排序。

## 为什么纯向量检索不够

M3 的向量检索很强，但有一类查询它天生不敏感：

| 查询类型 | 例子 | 向量路表现 |
|---|---|---|
| 同义改写 | "怎么让水更甜一点" | 好（匹配到"提高甜度"） |
| 型号/编号 | "bm25 算法"、"错误码 E1045" | 差——编号没有语义分布，向量化后被语义噪声淹没 |
| 罕见专名 | "蒙克法" | 差/不稳 |
| 精确短语 | 文档里必须出现这串字 | 无法保证 |

互补方案：传统全文检索（FTS5 + BM25）擅长字面匹配。两路各自召回，再用**排名融合**合成一个顺序——而不是笨拙地把两个分数加起来。

## 数据流

```
查询
 ├─ 语义路：embed → HNSW searchKnn(20 候选)          [按 cosine 距离排名]
 └─ 关键词路：
     buildQueryTerms(query)
       ├─ 英文/数字：整词
       └─ 中文：滑动三元组(trigram) + 整段短语
     → chunk_fts MATCH "三元组" OR "三元组" …（BM25 排名，JOIN document 限库）
                    │
                    ▼
     reciprocalRankFusion(vectorIds, keywordIds, k=60)
                    │  score = Σ 1/(60 + rank + 1)
                    ▼
     lexicalBoost（覆盖率 .15 / 精确短语 .10 / 标题命中 .05，有界 ≤.30）
                    ▼
     chunksByIds 取回原文 → topK=6 → 注入提示词（后续同 M3）
```

开关：设置里 `hybridSearchEnabled`（默认开）。关掉就退化为 M3 纯向量路，retriever 里一个分支的事。

## 核心知识点

### 1. 中文全文检索为什么必须用 trigram

SQLite FTS5 自带的 `unicode61` 分词器按空格/标点切词，中文整句没有空格，会被当成**一个** token——搜任何子串都不命中。

`tokenize='trigram'` 把文本切成连续的三字元组：`手冲咖啡水温 → 手冲咖/冲咖啡/咖啡水/啡水温`。查询也切成三元组做 OR 召回，天然支持中文、日文等无空格语言，且是子串匹配（不需要词典、不需要 jieba，零依赖）。

### 2. trigram 的脾气（全是实测）

- 最短匹配单元是 **3 个字符**。查"闷蒸"这种 2 字词 FTS 无能为力——代码里直接返回 null 跳过关键词路，让向量路独挑
- 中文长句**不能整串加引号**：`"二氧化碳排出"` 要求连续子串，匹配不到"二氧化碳充分排出"。必须切三元组再 OR，排序交给 BM25 按命中数算
- 原子全部双引号包裹，且先用正则白名单过滤输入——用户可能在查询里输入 `* ( ) ^ " :` 这些 FTS 语法字符，不过滤就是 MATCH 注入
- 原子数封顶 64，防超长查询把 MATCH 表达式撑爆

### 3. RRF：为什么"只看排名"是对的

cosine 距离范围约 0~2，BM25 是无界的、还可能是负数——两者尺度完全不同。常见的错误做法是 min-max 归一化后加权相加：在只有 20 个候选的小集合上，min/max 被一个极端值带飞，权重形同虚设。

Reciprocal Rank Fusion（Cormack et al. 2009）的公式：

```
score(d) = Σ_路 1 / (k + rank_路(d) + 1)      // 项目取论文经验值 k=60
```

- 第 1 名贡献 `1/61 ≈ .0164`，第 2 名 `1/62 ≈ .0161`……排名越靠后边际差越小
- 两路都命中的片段自然排到最前（语义和字面双重证据）
- 对分数分布完全免疫，无需调归一化——这也是 Elasticsearch / Meilisearch 的默认融合法

### 4. 重排加分为什么要有界且小

`lexicalBoost` 总分 ≤ 0.30，而 RRF 相邻名次差约 0.0004~0.016 量级……这里的设计意图是：**词法加分只在伯仲之间偏向字面更贴的片段，不能颠覆 RRF 的大盘**。覆盖率（查询的三元组有多少真出现在文本里）、精确短语、标题命中三个信号各有上限。

注意这是一个**接缝**：将来要上 cross-encoder（如 bge-reranker）做模型精排，只需替换这一步，retriever 的双路召回和 RRF 不用动。

### 5. 宽召回、窄融合

两路各召回 20 个候选（`RECALL_CANDIDATES`），融合重排后才取 6 个进提示词。先宽后窄：召回阶段怕漏（所以 OR、所以候选多），精选阶段怕噪（所以 RRF + 重排 + topK）。

## 深入：BM25、MATCH 表达式与 RRF 的数值演算

### A. BM25 到底在算什么（SQL 里的那个 `bm25(chunk_fts)`）

FTS5 内置的 BM25 给每个"文档 × 查询"打一个相关性分，直觉由三部分组成：

1. **词频饱和（TF）**：一个词在 chunk 里出现越多越相关，但边际递减——出现 10 次的价值远不到 1 次的 10 倍（BM25 用饱和函数压上限，防止靠重复刷词霸榜）；
2. **稀有度（IDF）**：词越罕见越值钱。"错误"在所有文档都出现，区分度低；`e1045` 只在一个 chunk 出现，命中就是强信号；
3. **长度归一**：同样命中两个词，500 字的 chunk 比 5000 字的 chunk 得分高——长文档天然包含更多词，不惩罚长度就会通吃。

SQLite 的 `bm25(chunk_fts)` 返回值是上述综合的一个**负数**（越负越好，所以 SQL 里直接 `ORDER BY bm25` 升序）。我们不直接消费它的数值，只消费它产出的**排名**（喂给 RRF），所以"负分、尺度无界"这些性质对下游无害。

### B. 一句自然语言怎么变成 MATCH 表达式：buildQueryTerms 走读

输入 `"E1045 闷蒸咖啡"`，[hybrid.ts](../../src/main/services/rag/hybrid.ts) 的产出：

```
英文/数字词（正则白名单）："e1045"            → atom + phrase
中文连续段 "闷蒸咖啡"：滑动三元组 → "闷蒸咖"、"蒸咖啡"  → atoms + trigrams
                        整段（≥2 字）         → phrase（供精确短语加分）
matchExpr = '"e1045" OR "闷蒸咖" OR "蒸咖啡"'
```

三个设计要点，每个都对应一次真实的失败教训：

- **为什么三元组 OR 而不是整串加引号**：`"闷蒸咖啡"` 作为短语要求四个字连续出现，资料写的是"闷蒸阶段的咖啡"就匹配不到——召回阶段宁滥勿缺，切成三元组 OR 后由 BM25 按命中数量排相关性；
- **为什么所有原子加双引号**：FTS5 MATCH 有自己的语法（`*` 前缀通配、`:` 列过滤、括号分组）。用户输入 `a) OR b*` 若直接拼接，等于把查询语法权交给了用户（MATCH 注入）。白名单正则先滤掉所有非法字符，再把每个原子包成引号短语原子——引号内一切皆字面量，OR 是我们自己代码拼的，用户无法改变布尔结构；
- **2 字词为什么直接放弃**：`闷蒸`切不出任何三元组，强行查询得到空表达式甚至报错。`buildQueryTerms` 返回 null，retriever 跳过关键词路整条（不是返回空结果！），由向量路独挑。

### C. SQL 里真正发生了什么

[repo.ts](../../src/main/services/knowledge/repo.ts) 的 `searchChunksByKeyword`：

```sql
SELECT c.*, d.file_name AS doc_name, bm25(chunk_fts) AS bm25
  FROM chunk_fts
  JOIN chunk c ON c.id = chunk_fts.chunk_id
  JOIN document d ON d.id = c.document_id
 WHERE chunk_fts MATCH ?          AND d.kb_id = ?
 ORDER BY bm25
 LIMIT ?
```

执行顺序（SQLite 查询计划的语义）：先用 MATCH 走 FTS 倒排索引召回候选（毫秒级，不全表扫描）→ JOIN chunk 拿正文和 meta → JOIN document 并施加 `kb_id = ?` 合取过滤 → 按 BM25 排序取前 20。注意 `MATCH ... AND d.kb_id=?` 是同一 WHERE 的两个合取支，MATCH 内部拼的那些 OR 无法越过 AND 冲掉知识库边界——库边界永远是硬过滤。`chunk_fts` 里不存 kb_id 是刻意的：少一个需要与 chunk 表保持一致的冗余列。

### D. RRF 数值演算：亲手算一遍就懂了

公式（rank 从 0 起，代码里 +1 转成 1-based）：

```
score(d) = Σ 1 / (60 + rank + 1)
```

假设两路各召回 20 个，观察 4 个有代表性的 chunk（`v`=只在向量路，`k`=只在关键词路，`b`=两路都有）：

| chunk | 向量路排名 | 关键词路排名 | 计算 | 总分 |
|---|---|---|---|---|
| b1 | 1 | 3 | 1/61 + 1/63 | ≈ 0.03228 |
| b2 | 2 | 1 | 1/62 + 1/61 | ≈ 0.03252 |
| v1 | 3 | — | 1/63 | ≈ 0.01587 |
| k1 | — | 2 | 1/62 | ≈ 0.01613 |

读法：

- **两路都靠前的 b1/b2 稳居头部**（两份贡献叠加，约 0.032）；
- 单路候选 v1/k1 不会消失，但天然排在双路命中之后；
- 注意 k1（关键词第 2）略高于 v1（向量第 3）——在"另一路没表态"时，单路排名也能决定次序；
- 第 1 名贡献 1/61≈0.0164，第 20 名 1/80≈0.0125——**头部和尾部差距很小**，这正是 k=60 的作用：让融合对单路内部的具体名次不要太敏感，只保留大致梯序。这也意味着 RRF 分差非常接近的候选很多，最终次序交给下一步词法微调。

对比"归一化加权相加"为什么崩：假设向量路第 20 名的 cosine 距离恰好是个离群值（0.9，其他都 0.3~0.5），min-max 归一化后其他 19 个候选全被压到 0.8~1.0 的窄区间，手工权重 0.5/0.5 瞬间失效。RRF 根本不读距离数值，这类离群值对它不存在。

### E. lexicalBoost：在 RRF 的小分差上做有界微调

RRF 相邻名次差约 0.0002（第 1、2 名差 1/61−1/62≈0.00027，第 20 名附近约 0.00015），词法加分（[hybrid.ts](../../src/main/services/rag/hybrid.ts) `lexicalBoost`）总量封顶 0.30，三个有界分量：

```ts
return 0.15 * coverage        // 查询三元组在 chunk 里真实出现的比例
     + 0.10 * phraseHit      // 英文词/中文整段连续出现的比例（型号名级强信号）
     + (inHeading ? 0.05 : 0) // 查询词出现在 headingPath 面包屑里
```

用 D 节的数字感受尺度：RRF 双路头名约 0.033，而 boost 最大 0.30——**这不是"微调"，而是有意让强词法信号可以翻盘**。但能拿到高 boost 的前提苛刻：coverage 要 0.15 必须三元组几乎全部命中，phrase 要 0.10 必须完整型号/专名连续出现，0.05 还要标题命中。同时满足这三条的文本，本身就是关键词式查询（`E1045`、`bm25`）最可能的正确答案——等于在词法路擅长的查询类型上把决定权交给词法。反过来，泛泛的标题命中只值 0.05，且这样的块至少已被某一路召回（本身已有一定相关性），噪声可控；语义相关但字面不重合的向量候选 coverage≈0，而 **boost 只加不减，语义路候选不会被惩罚**。

### F. retriever 编排：一路挂了，问答不能挂

[retriever.ts](../../src/main/services/rag/retriever.ts) 把纯函数串成管线时有两个工程决策值得学：

- **向量路始终执行，关键词路 try/catch 降级**：FTS 表损坏、MATCH 表达式异常（理论上被白名单挡住，防纵深）都只 `console.warn` 后降级纯向量检索——检索是问答主链路的一环，增强能力不能成为单点故障源；
- **顺序回填保序**：两路召回的是 id 排名，取正文用 `chunksByIds` 一次 IN 查询拿回，但 SQL IN 不保证返回顺序，必须在内存按两路融合后的 id 顺序重排，否则 RRF 白算了。

## 踩坑记录

- **FTS 内容同步不要用触发器**：chunk 只有"批量插入"和"随文档删除"两个写路径，在仓储同一事务里顺手写 `chunk_fts` 最直观可控；触发器会让数据流向变成隐式魔法，排查问题极痛苦
- `chunk_fts` 不冗余 kb_id，库过滤靠运行时 JOIN document——少一份要维护一致的冗余数据
- 老用户已有 chunk 数据：建虚表后 `runMigrations` 用一条 `INSERT … SELECT … WHERE NOT EXISTS` 回填一次，同样幂等

## 自测题参考答案

**1. 分别举一个纯向量检索答得好、纯关键词检索答得好的查询，并解释原因。**

- 纯向量答得好："怎么让手冲咖啡甜一点"——资料里可能根本没有"甜"这个字，写的是"适当提高注水温度并缩短萃取时间可降低苦涩、突出甜感"。字面零重合但语义相近，embedding 把两者映射到向量空间的邻近区域，HNSW 能召回；关键词路搜"甜"字反而什么都搜不到。
- 纯关键词答得好："bm25 算法怎么配置"或"错误码 E1045"。型号/编号/缩写没有语义分布：`bm25` 不是一个"意思"，就是四个字符的 token；`E1045` 向量化后被周围大量语义噪声淹没，cosine 排名极不稳定。FTS5 + BM25 走精确子串/词项匹配，只要文档里出现这串字符就能高相关性召回（trigram 对 `bm25`、`e1045` 这类字母数字串按整词处理）。

这正是双路并存的理由：语义路解决"换个说法"，关键词路守住"字面必须准"。

**2. 为什么不能把 cosine 分数和 BM25 分数归一化后直接相加？RRF 从数学上回避了什么问题？**

两路分数的尺度完全不同：cosine 距离是约 0~2 的有界值；BM25 无界、还可能为负，数值随文档长度、词频、文档集统计量变化。min-max 归一化看似对齐了尺度，但在每路只有 20 个候选的小集合上，min 和 max 本身就是两个随机样本——一个极端候选（特别长的文档、罕见词项）就能把其他 19 个的归一化值全部压扁，手工权重（0.5/0.5 之类）随即失效。不同查询之间归一化后的分数也不可比。

RRF 只使用**排名**：`score(d) = Σ 1/(k + rank + 1)`，k=60。它回避了"分数分布不可比"这个根本问题——不读取任何一路的绝对分数，因此对尺度、离群值、单调变换全部免疫。两路都排第一的片段拿两份约 0.0164 的贡献自然居首；只在一路出现的候选也不会消失。代价是丢失了"领先多少"的强度信息，所以后面才用有界的 lexicalBoost 在排名接近时做词法微调，而不是回到分数相加。

**3. trigram 分词器对 2 字中文词为什么无能为力？产品上怎么兜底？**

trigram 的最小 token 是连续 3 个字符：索引端"闷蒸"只能切出 0 个三元组（长度不足 3），查询端同样切不出任何词元，MATCH 表达式为空——天然无法匹配（这是 FTS5 trigram 分词器的硬约束，不是配置问题）。

兜底：`buildQueryTerms('闷蒸')` 直接返回 null，retriever 跳过关键词路，由向量路独挑——2 字词通常是有语义的普通词（"闷蒸""醒豆"），embedding 反而能靠语义近邻找到相关段落。这也是"两路互为备份"设计的一部分：词法路有最小长度边界，语义路没有。1–2 个英文字母的查询同理处理。

**4. 用户在搜索框输入 `a) OR b*`，从输入到 SQL 绑定经过了哪些防护？**

三层：

1. **白名单清洗**：`buildQueryTerms` 先用正则只保留字母/数字/CJK 等安全字符，`)`、`*`、空格这类 FTS 语法字符直接被滤掉，不会进入查询表达式——防止用户输入闭合引号、注入 `OR *` 之类改变 MATCH 语义（MATCH 注入）。剩下的 `a`、`b` 作为英文/数字整词保留。
2. **结构化构造**：每个词元都用双引号包成语法安全的短语原子（`"a" OR "b"`），原子数封顶 64，超长查询不可能把表达式撑爆；中文另走三元组 OR 召回。
3. **参数化执行**：MATCH 表达式和 kbId、limit 全部作为 better-sqlite3 的绑定参数传入（`MATCH ?`），不是字符串拼进 SQL——即使清洗漏网，也无法逃逸成 SQL 注入；库过滤是 MATCH 之后 JOIN document 的合取条件，OR 只在 MATCH 内部作用，冲不掉知识库边界。

**5. `lexicalBoost` 为什么设置 0.30 的总上限而不是直接按特征排序？**

因为大盘必须由 RRF 决定，词法信号主要用来"在伯仲之间偏向字面更贴的候选"：

- RRF 相邻名次的分差很小（头部相邻约 0.00027），三个词法特征（覆盖率 0.15 / 精确短语 0.10 / 标题命中 0.05）各自有界、总和 ≤ 0.30；
- 需要注意 0.30 相对 RRF 头名（约 0.033）其实是"可翻盘"量级——这是**有意的**：拿满 boost 需要同时满足"三元组全覆盖 + 精确短语连续出现 + 标题命中"，这种文本本就是型号/编号类关键词查询最可能的正确答案，等于让词法路在它擅长的查询类型上握有决定权；
- 安全垫在于：能被 RRF 融合的候选都先经过了某一路的 20 强召回（纯靠标题词、正文一个查询三元组都不含的块，coverage=0、phraseHit=0，最多 0.05，且没有召回资格就根本进不了融合集），boost 只加不减（语义候选不会被惩罚）。
- 这三个信号本身都有噪声：标题短、术语重复会让"标题命中"虚高；三元组覆盖率高不等于回答了问题。所以权重是按"完整词法证据才给大分、结构性弱信号给小分"分配的经验值。

它还是一个**可替换的接缝**：将来上 cross-encoder reranker，只需把 lexicalBoost 换成模型打分的重排函数，双路宽召回 + RRF 候选融合 + topK 精选的骨架不动。

**6. 想把混合检索升级成"召回后用 reranker 模型精排"，应该改哪个函数？哪层接口保持不变？**

改 [hybrid.ts](../../src/main/services/rag/hybrid.ts) 里的重排环节（用 cross-encoder（如 bge-reranker）对"查询 × 每个候选片段"逐对打分，替换/包在 `lexicalBoost` 外面）。cross-encoder 是异步的、要调模型，实际落地通常在 retriever.ts 的编排处插入一个 `rerank(query, candidates, topK)` 异步步骤（把现在的纯函数 lexicalBoost 收编为模型不可用时的 fallback）。

保持不变的层：双路召回（embed → HNSW 20 候选；buildQueryTerms → FTS 20 候选）、`reciprocalRankFusion` 的候选合流、以及 retriever 对外的接口（输入 kbId+query，输出带序号的 topK 片段）和下游一切（提示词拼装、citation 事件、message.meta、UI 角标）都不用动。这就是"宽召回、窄融合"分层的收益：召回追求不漏，精排追求不噪，两层可以独立升级。
